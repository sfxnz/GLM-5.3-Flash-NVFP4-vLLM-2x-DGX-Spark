# v15 image layer: fixes

`Dockerfile.sm121-v15` builds on `glm53-sm121-v14` and adds two Python-only patch layers: `patch_v15_fixes.py` (the three switches below) and `patch_v15_kda_recover.py` (`GLM53_KDA_RECOVER`, documented in `README-v15-kda-recover.md`). Each switch is a `GLM53_*` environment variable and is off in the image. With none set, v15 runs v14's code.

```bash
docker build -f docker/Dockerfile.sm121-v15 -t glm53-sm121-v15 docker
GLM53_V14_SRC=/path/to/v14src python3 docker/test_v15_fixes.py   # source tests on the host
docker run --rm --network none -v "$PWD/docker:/t:ro" --entrypoint python3 \
  -e GLM53_V14_SRC=/usr/local/lib/python3.12/dist-packages glm53-sm121-v14 /t/test_v15_fixes.py   # plus behaviour tests, CPU only
```

`GLM53_V14_SRC` is the directory that holds the `vllm/` tree copied out of `glm53-sm121-v14`. The behaviour tests need torch, so on a bare host they skip; in the CPU-only container they run the patched scheduler, KV cache manager, video processor and the MLA clamp kernel (Triton CPU interpreter). `GLM53_SNAPSHOT` and `GLM53_VIDEO_CLIPS` add an end-to-end video test with the real checkpoint processor. Build once on the head and ship it (`docker save glm53-sm121-v15 | ssh spark2 docker load`).

The switches go through `EXTRA_ENV`. `run.sh` refuses its knobs on an image tag that is not `glm53-sm121-v13*` or `v14*`, so boot v15 with `FORCE_UNSAFE_IMAGE=1` until that guard knows v15.

## Why the prefix-cache mechanism changed

The serve's KV groups are the MLA group at 4608 tokens (fp8 KV makes vLLM raise `--block-size 2304` to 4608 so the attention page holds a KDA state page, `Setting attention block size to 4608` in every boot log), the kpool tail, the DFlash draft group at a quarter of that (1152, `patch_v11_dflash_kv_groups.py`), and the KDA groups in align mode at 4608. EngineCore sets `cache_config.block_size` to the smallest prefix-cacheable group (`v1/engine/core.py:329`), which is the draft group: 1152. Hits are aligned to 4608, the LCM, because the kpool tail turns fine-grained hits off.

- v13's `GLM53_DFLASH_PREFIX_CACHE_FIX` (Tony's port) keeps the EAGLE last-block drop on the draft group and lets the draft never shrink the target's hit. DFlash does not need the drop: the speculator writes every target position's draft context K/V from that position's hidden state alone (`spec_decode/dflash/speculator.py`, `precompute_and_store_context_kv`). The never-shrink rule then leaves the draft window over the cached span unwritten when the draft blocks were evicted, so the drafter reads stale pages. Lossless, but it costs acceptance and reads garbage.
- vLLM #54163 removes the drop for DFlash at the source. The fixed-point search then shrinks a hit to a boundary that every group holds, including the draft window. That is correct by construction, so v15 turns the v13 rule off when its switch is on.
- Neither upstream PR touches the split unit, because upstream's packed layout has no smaller draft group. The align split's invariant ("slot p holds the state after exactly (p + 1) * block_size tokens") needs the KDA block, so v15 reads it from the KDA group's spec.

The CPU test runs the real `_get_kv_cache_groups_glm5_next`, `KVCacheManager` and `_mamba_block_aligned_split` on this layout. Switch off: a 9216-token repeat hits 0. With a 4600-token prefill budget, a 4608 hit restores the state after 3456 tokens. Switch on: 9216 → 4608, 13000 → 9216, each with the matching state and the draft blocks.

## Why the MLA clamp is safe on FA2

- FA2 (`batch_mla_plan.cu`) and FA3 fill the same `MLAPlanInfo` from `MLAPlan` (`attention/scheduler.cuh`). The work arrays sit at the plan-info offsets with 16384 slots each.
- The FA2 kernel (`attention/mla.cuh`) bounds its tile loop and the non-causal logits mask by `kv_end`. A work with `kv_end <= kv_start` writes zeros with lse -inf (`write_empty_o`).
- The split-KV merge folds partials in `kv_start` order. Chunk 0 starts at 0 and keeps at least one token (a row's valid count is at least 1), so a clamped-empty later chunk contributes `exp2(-inf - m) = 0`, never NaN.
- Loads in the last tile are predicated by the planned `kv_len`, which can now exceed the valid count. Our builder lays rows out at a fixed `topk_width` stride (upstream uses a cumsum), and the planned length is capped at `index_topk + kpool - 1 <= topk_width`. Those reads stay in the row's own slice, whose -1 tail `forward_mqa` already clamps to slot 0, and the mask drops them.
- Our `GLM53_ADAPTIVE_VERIFY` masks rows but keeps every shape, so the host query split equals the device one. vLLM's own adaptive verification, if enabled, falls back to bounding every row by the batch max.
- The CPU test runs the clamp kernel under the Triton interpreter on a mirrored plan layout. Each row's clamped works cover exactly the exact valid count, growth within the slack reuses the plan, and growth past it replans.
